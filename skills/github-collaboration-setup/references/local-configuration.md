# Local configuration: scan, plan, diff, apply

Use after [preflight](preflight-and-identity.md) and [authorization](authorization.md) for `initialize`, `upgrade`, or `repair`. The current actor must have an effective Leader or scoped Bootstrap/Recovery grant. A plan is read-only; no plan, prior chat message, or operation record grants authority. Consult [managed resources](managed-resources.md) for ownership and non-Markdown merges, and [resume and recovery](resume-and-recovery.md) after interruption.

## Scan before proposing a file change

1. Resolve the verified project root, Git status and HEAD, default-branch governance source SHA, and every intended path. Inspect each component of the path with `lstat`; stop on a symlink, non-regular target, or traversal outside the verified root. Do not follow a suspicious link to read or write it.
2. Read the current target bytes, not just rendered text. Identify whether it is tracked, modified, staged, untracked, or absent. An existing `AGENTS.md`, `CLAUDE.md`, project document, or GitHub template belongs to the user unless exact managed ownership is established. Stop on a dirty target. Ask for two separate choices: how to handle the existing edits while preserving the original bytes or using a reviewed merge/defer plan, and whether those uncommitted edits enter this governance Commit. “Keep my words”, “do not delete”, or “you decide” does not settle Commit ownership.
3. Check exact managed markers, then scan for semantically similar but unmanaged instructions. Duplicate or damaged markers, overlapping rules, and unknown ownership require the user's explicit choice. A name or path match alone is not ownership.
4. Read the installed manifest and previous verified baseline. Resolve every canonical asset from the bundled Skill package. Verify the full package's immutable source, file list and digests at installation/update or when no trusted validation record exists. In an unchanged session, reuse that result after checking the effective package path/version and relevant asset digests; source, path, version or content drift invalidates it. A source-tree copy is acceptable only during development, with the reviewed source version recorded. Do not render from an unverified downloaded template or interpret each local action as a new full-package download.
5. Inventory each proposed local and remote resource as a separate item, including existing protections. Identify the configured authorization file as an explicit governance artifact outside generic automatic whole-file upgrades. If the registry already tracks it, resolve the retention/migration choice through [managed resources](managed-resources.md) before preparing `P`/`E`; preserve the original entry and baseline history. If a baseline cannot be recovered, stop a supposed upgrade and offer a reviewed takeover or leave-untouched option; never invent an ancestor for a three-way merge.

## Governance review and managed ownership

Review each entry in trusted `managed_paths.entry_files` as a complete governance file; when the field is absent, the checker uses `AGENTS.md`, `CLAUDE.md`, and `CONTRIBUTING.md`. This includes ordinary prose and installation links outside the managed block. Nested `AGENTS.md`/`CLAUDE.md`, `AGENTS.override.md`, and instruction-loading resources also need governance review. Check both paths on a rename. A missing patch preserves that routing and leaves the actual changes awaiting a reviewable diff; it is not evidence that the change is harmless. Inspect other changed paths for effects on entry or installation-link reachability.

That review scope grants no whole-file ownership. Render only the approved managed block and preserve outside bytes. A user-owned prose or link edit, relocation, or new managed-resource takeover needs its own ownership decision, exact diff and explicit approval. Keep dirty-file treatment and Commit ownership as separate choices; the candidate's preservation of user words does not authorize including those edits in a governance Commit.

## Project context and collaboration choices

Populate the context index in `.github/agent-collaboration/README.md` from the project's existing README, entry files, PRD/requirements, SPEC/design, decision records, plans/progress and validation evidence. Follow actual repository references and accessible GitHub links; inspect each source before assigning its purpose. Record the exact path or URL, the fact category it governs, and any confirmed current version/status. A category may need several non-overlapping sources; each fact has one authoritative source. Keep other useful documents as supporting links, not competing copies. Missing, inaccessible or conflicting sources stay `未知` with the unresolved choice; do not invent document names, owners, dates, status or facts, and do not create empty PRD/SPEC files merely to fill the index. Present changes to existing index rows as a reviewed incremental diff. The installation candidate is complete only when every category has a verified pointer or an explicit unknown; this does not certify the underlying project is complete.

Read `branch_policy.integration_branches` from the active config; absence means an empty list. If the project needs an integration branch, propose its exact `agent/<actor_id>/issue-<primary_issue>-<description>` name, responsible actor, parent Issue, verified baseline SHA and review/merge protections as a separate config diff. Register approved integration branches through default-branch governance before using them as collaboration bases. New task branches may start at a verified SHA of the default branch or an already registered integration branch. Integration merges are intermediate results; final delivery still requires acceptance and a PR to the default branch. All authorization continues to come from config and its selected records at one verified default-branch SHA.

Retain the project's Issue and PR body structure, including structures chosen by its engineering tools. Preserve task outcome, scope, acceptance, real validation, risks/rollback and remaining work without imposing headings or another tool's configuration. Research and decision tasks may complete with an accepted durable result linked from their Issue; repository-file changes still use a branch and PR. Important handoffs belong in a repository artifact or GitHub record that a later session can read.

For setup work, create the governance Issue and record its scoped claim before implementation, Commit or Push; creating the Issue, claiming it for the first time, commenting and independently reviewing do not require a prior implementation claim. Validate the claim with the bundled `assets/schemas/collaboration-event.schema.json`: record actor/account/session, Issue, scope, planned branch and verified base/HEAD, then retain the posted comment URL as evidence. Use the selected PR template's **one** `agent-collaboration:metadata` JSON comment with `workflow: "setup"`; fill every identity, version, primary Issue, close list, claim URL, base and HEAD field from verified state. A primary Issue may remain open for partial delivery; any explicit closing statements must match the deduplicated `closes_issues` list. Refresh claim and remote HEAD before Push, update the metadata after new commits, and refresh authorization/account permission before formal review, merge and governance actions. The metadata is a declaration for inspection, not proof of loaded Skills or an actual running process.

## Build an approval-bound plan

Allocate one stable `operation_id` for the attempt and record it under the chosen local audit location. Include repository hostname and immutable ID, owner/name, default branch and source SHA; current branch/HEAD; actor ID, controlling account ID and session ID; mode; resource kind and stable path/remote ID; template version and verified baseline reference; exact current and proposed SHA-256 digests; the diff or field-level change; existing protections; per-item approvals with external evidence and scope; completed remote IDs; read-back results; and `next_safe_action`. Mark a missing file as `absent`, rather than hashing an imaginary empty file. Never put tokens or secrets in the record. This is resume/audit data, **not an authorization source**; recheck the default-branch grant, account permission and human approval before a write.

For Markdown entry files, use this Skill package's `scripts/managed_block.py plan` candidate renderer or an exact manual equivalent. It reads a regular source and creates a separate candidate; it never edits the source. The body comes from the reviewed managed-block asset. The candidate must preserve every byte outside one exact block, including BOM and line endings. If there is no block, it may append only the necessary separator and new block. Record the renderer's `original_sha256` and `candidate_sha256`, show the byte-aware diff, and ask approval for that exact candidate. A render error or similar unmanaged rule is a stop, not a license to rewrite the file.

For a dirty entry file, show the existing unstaged and staged diffs, the exact candidate file diff, and the proposed staged diff for the governance Commit. Get the user's explicit treatment and Commit-ownership choices before writing or staging; approval of the file diff alone does not approve staging or Commit. If the user's edit and managed block form an inseparable hunk, **Do not stage the whole file** to meet a deadline. Offer a separately reviewed user Commit, a verified isolation plan that stages only approved content, or deferral; let the user choose. If no separation can be verified, stop rather than include an unapproved edit.

For authorization, follow [authorization](authorization.md) for the explicit governance diff, `P`/`E` approvals and read-back; use [managed resources](managed-resources.md) to resolve existing registry conflicts first. For `config.yml`, Issue Forms, PR templates, workflows, CODEOWNERS, Labels, Rulesets and branch protection, follow the managed-resource procedure. Do not use a Markdown append, blind YAML serialization, whole-object remote `PUT`, or path/name coincidence as a replacement for schema and ownership checks.

Present the plan as numbered resource diffs. For each item state: current digest or `absent`, proposed digest, ownership/baseline confidence, possible effect, effective permission, existing protections, exact intended action, and approval still needed. Ask the user to choose how to handle every overlap or conflict. File-diff approval does not include staging, Commit, Push, PR, Actions execution, or a remote setting; obtain those approvals at their respective steps.

## Apply one approved local item

1. Re-read repository identity, default-branch authorization and protections, account permission, worktree status, target type/path, current bytes and relevant managed fields. Recompute their digest. If the source SHA, target HEAD, path ownership, permission, or digest differs from the approved plan, stop this item and generate a new diff for approval.
2. Confirm the approved candidate digest still matches the candidate bytes. Apply only the approved managed-block change or separately approved resource candidate, preserving unrelated content. Whole-file governance review does not expand this write scope. Do not stage broad globs, use `git add .`/`git add -A`, reset, clean, force push, or overwrite an unknown user's changes.
3. Immediately read the target back as bytes, compare it with the approved candidate digest and check that the outside-block bytes and surrounding resources remain as planned. Record actual outcome, digest, timestamp, and next safe action. A failed read-back is unresolved, not success; leave other items untouched and report the exact state.

The pre-write check and write are not an atomic compare-and-swap. Another editor can change a file in that interval, and a pure Skill cannot lock every client. Disclose this concurrency window and treat any post-write mismatch as an incident for inspection rather than silently replaying the write.
