# Managed resources and ownership

Use this reference when a setup plan touches `.github/agent-collaboration/managed-resources.yml`, structured files, templates, CODEOWNERS, or remote GitHub settings. Read [local configuration](local-configuration.md) for the approval-bound plan and per-item apply loop.

The registry is a change baseline, not proof of Agent authority. Validate it with the bundled `assets/schemas/managed-resources.schema.json` using JSON Schema Draft 2020-12 and `FormatChecker()`. Each entry needs `kind`, `stable_id`, `template_version`, `managed_fields_baseline_digest`, `applied_digest`, and `baseline_reference`; SHA-256 values use `sha256:<64 lowercase hex>`. Keep the verified previous bytes/managed-field snapshot at a recoverable `baseline_reference`. Do not store credentials. Include the registry itself in the reviewed governance diff; do not let an edit to it retroactively claim ownership of an existing resource.

| Resource | Ownership and merge procedure |
| --- | --- |
| `AGENTS.md`, `CLAUDE.md`, ordinary Markdown | Own only one exact `github-agent-collaboration` block. Use the candidate renderer; preserve all bytes outside it. Duplicate, malformed, or similar unmanaged content stops. |
| `config.yml` | Validate current, baseline, and candidate against the bundled config schema with `FormatChecker()`. Compare fields and render an exact text diff; preserve unknown fields, comments, ordering, and unrelated bytes. If the chosen edit method cannot do that reliably, stop and ask for a manual merge. |
| Configured authorization file | Review each change as an explicit governance artifact through [authorization](authorization.md), outside generic automatic whole-file resource upgrades. Validate the record and exact field/text diff, preserving prior grants, unknown fields, comments, ordering, and unrelated bytes. Resolve existing registry ownership below before `P`/`E`; a proposed record never authorizes itself. |
| Issue Forms, PR templates, workflows | A new path must be unoccupied. For a previously managed path, compare verified last-applied bytes (ancestor), current bytes (user changes), and new bundled template (proposal). Auto-update only unchanged managed portions; overlapping edits or missing ancestor require an explicit choice. Validate relevant YAML before approval and after read-back. |
| CODEOWNERS | Preserve existing lines and order. Evaluate later-pattern precedence and actual matching ownership; verify accounts/teams are eligible. Any change to existing ownership, or uncertain interpretation, needs a separate explicit approval. |
| Labels, Rulesets, branch protection | Identify the exact repository and stable remote ID. Compare only recorded managed fields against the last-applied field snapshot, current remote fields, and proposed values. Preserve all unowned fields and stricter existing/organization protections. Same name alone does not permit takeover. |

For a new installation, keep authorization out of generic automatic whole-file registry ownership and retain its exact approved diff, final approval, and read-back as external governance evidence. If an existing registry already tracks the configured authorization path, stop before `P`/`E` and show the entry, stable ID, recoverable baseline, prior/current digests, and the conflict: an evidence-only `E` changes the authorization digest, while changing the registry in `E` would violate the evidence-only comparison. Ask for an explicit decision: retain the entry and defer the authorization change until a separately reviewed non-circular maintenance plan exists, or approve a separate migration out of automatic ownership. A migration must retain the original entry and baseline as recoverable audit history and show the exact registry diff; never silently delete ownership history or invent an automatic upgrade. Until the chosen plan is approved and verified, leave the entry and authorization bytes intact.

For structured and remote resources, produce a field-level three-way report: `baseline → current` shows user drift, `baseline → proposed` shows template change, and `current → candidate` is the exact requested edit. A verified unchanged baseline may be applied only to approved managed fields. If both user and template changed the same field, or a baseline/reference is unavailable, stop and show alternatives: retain current, manually merge with reviewed bytes/fields, select a different path/resource, or explicitly take over. The user must choose and approve the resulting exact diff. Existing branch protections are not weakened to make a candidate pass.

For each registry update, bind the kind and stable ID, template version, prior baseline reference/digest, and the newly read-back applied digest. The digest basis must be explicit: entire local file bytes for a file; a deterministic serialization of **only the named managed fields plus stable ID** for a remote object. Use the same field selection and serialization for baseline, approval and read-back; if it cannot be reproduced, stop instead of declaring a match. Record unrelated fields separately to prove they were preserved. The template's raw `__SETUP_REQUIRED__` placeholders are never an installed value.

Apply one item only after fresh identity/authorization and current-digest checks, then read back by path or stable remote ID and record the result. For a newly created remote object, store its returned stable ID and look it up before declaring success. If a request times out, query the object by the known ID; for creation with no ID yet, query the exact repository/type/name or path and compare candidate fields. Ambiguous matches stop. Never blindly repeat a possibly successful mutation.
