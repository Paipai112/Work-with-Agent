# Remote GitHub governance: inventory, diff, approval, read-back

Use this reference after [preflight](preflight-and-identity.md), [authorization](authorization.md), and [managed resources](managed-resources.md) for Labels, repository settings, templates, CODEOWNERS, required checks, Rulesets, and branch protection. For Actions execution and protection mechanics also read [Actions and Rulesets](actions-and-rulesets.md). `diagnose` is read-only. A remote plan or a previous approval never grants Leader status.

## One item at a time

1. Identify GitHub host, immutable repository ID, owner/name, default branch and source SHA, authenticated account ID and current permission, effective Agent Leader grant/ceiling, applicable organization policy, current branch rules, and exact resource ID. Read all pages of lists. Treat 403/404 or missing fields as unknown until identity and feature availability are resolved; a name match is not managed ownership.
2. For each candidate, record `kind`, stable ID or `absent`, current endpoint/path and fields, verified previous managed-field baseline/reference, field selection, and current digest. For remote objects digest a deterministic serialization of the **stable ID plus only named managed fields**. Keep untouched fields separately. For local files use exact bytes and their SHA-256. Show `baseline → current`, `baseline → proposed`, and `current → candidate`, with effects on existing and inherited protections. If a baseline is missing, show a reviewed takeover or leave-untouched choice; never invent the ancestor.
3. Show a numbered, item-specific proposal: old/new values, what will remain, capability/plan uncertainty, effective permission, possible triggers/cost, exact endpoint or path, and the individual approval question below. An approval for one Label or setting does not cover another. Obtain a choice for overlap, a separately approved takeover, and the **current exact** diff before any mutation. Do not offer to reduce an existing stricter protection to make setup pass.
4. Before applying one item, re-read repository identity, default-branch grant and account permission, resource by stable ID, all relevant fields and digest. Drift, missing ID, conflicting source, altered protection, changed account permission or changed approved candidate invalidates this item's approval. Re-plan and ask again. Apply only the approved managed fields. Immediately GET the resulting resource by stable ID/path, compare fields and unchanged fields, record returned ID, digest, time and outcome. If a network request times out, query its stable ID; for creation without a returned ID, query exact repository/type/name/path. Ambiguous matches stop. No blind retries, bulk overwrite, deletion, or rollback of user state.

Pure Skill pre-read/write is not an atomic lock. Report any read-back mismatch and pause dependent steps for inspection.

## Approval sequence

Follow the applicable gates in this order. Skip a gate only when that operation is absent; no earlier gate implies a later one:

`local file diff → Commit → Actions trigger, runner and cost disclosure/approval → Push → create PR → each Label → each Actions setting → each Required Check → each Ruleset or branch-protection change`.

Local Issue/PR templates, workflow files and CODEOWNERS require their own file-diff approval before editing; Commit, Push and PR each require new approval. Workflow approval must precede **any** Push/PR/merge/dispatch that may run a new or existing workflow. CODEOWNERS effects on prior ownership need an additional explicit decision. A policy or check can be enabled only after its prerequisites are observed. [Actions and Rulesets](actions-and-rulesets.md) supplies those gates.

The optional v0.1 metadata job and its Required Check apply to final PRs targeting the default branch. Its job-level base condition skips execution on internal integration PRs without allocating a runner; a skipped job/check may still be visible and is not validation evidence. Registered integration branches use project review; preserve their existing protections, and never require this inapplicable check there. Adding an integration branch to config does not enable Actions or change a remote protection setting.

## Resource contracts

The `gh api` examples are **read-only discovery**. Replace `OWNER/REPO`, branch and IDs only with values returned from the verified target repository. Check the live [GitHub REST reference](https://docs.github.com/en/rest) for the host/API version, token capability, plan availability and exact write payload before applying. A current account's Maintain/Admin label alone does not prove an endpoint call is permitted; the effective Agent ceiling and actual endpoint right must both allow it.

After write GET protection and effective rules, compare all approved/untouched fields. |

For a proposed native Required Review or required CODEOWNER review, first prove an **additional eligible GitHub account** can review the PR. The author account cannot approve its own PR. Different Agents using that same account may leave separate protocol review evidence at the current HEAD, but GitHub sees one account; their comments are not native Approve. If only one account exists, defer the new native requirement and report the gap; if a requirement already exists, keep it and report the blocker. [GitHub review documentation](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/reviewing-proposed-changes-in-a-pull-request), [CODEOWNERS documentation](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners).
