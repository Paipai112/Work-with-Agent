# Actions, required checks, Rulesets and native review gates

Use with [remote governance](remote-governance.md) when a proposal can trigger GitHub Actions or change server-enforced protections. Read-only inventory is allowed in `diagnose`; every mutation requires current effective Leader authorization and the specific approval described here. GitHub can inspect declared metadata and check results, but cannot prove an Agent loaded a Skill. Shared account credentials cannot create independent GitHub review identities.

## Before a workflow can run

Before the **first possible trigger**, enumerate both the proposed workflow and all existing workflows matching the contemplated branch `push`, PR creation/update, merge or manual `workflow_dispatch`. A workflow committed to a branch can run on that branch's Push; wait until after Push to request approval and the gate has already been crossed. Display:

- Exact file diff, `on` events and activity/branch/path filters, any `workflow_dispatch`, runner type/OS, job steps and third-party dependencies, `GITHUB_TOKEN` permissions, secret/environment access, and PR code or data that jobs consume.
- Repository visibility and current Actions/organization policies, likely runs per Push/PR/merge/dispatch, expected minutes/storage/cache effects, and who is billed. Check the **current** owner plan, included usage, billing/budget setting and live GitHub pricing before stating a numerical limit or cost. Standard hosted runners in public repositories and self-hosted runners have different billing from private hosted runners; larger runners and storage can have separate charges. Treat unavailable billing data as unknown and ask whether the user approves execution with that uncertainty. [GitHub Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions).
- Whether the current Push is permitted by existing protections and whether the workflow file exists on the default branch. List trusted versus untrusted inputs, permissions and cache boundaries.

Ask separately: “在仓库 `<repo-id>`，是否批准这次 Push/PR/合并/手动触发可能运行所列 workflow（触发条件、Runner、预计频率、额度/费用不确定项如上）？” Bind approval to repository, exact workflow/setting digest, trigger and runner facts, operation and current SHA. If absent, stop before Push/PR/merge/dispatch. An alternative candidate that omits or disables the workflow is a **new** file diff and still needs the ordinary Commit/Push approvals; inspect existing workflows that may run. Repository Actions setting changes require their own independent approval and Admin-capable Agent; this execution approval does not enable Actions settings automatically.

### Trusted metadata check boundary

The v0.1 metadata job executes only for **final PRs whose base is the repository's default branch**. Its workflow, checker, config and authorization remain sourced from a verified default-branch SHA. The checker can recognize `branch_policy.integration_branches` for declared base validation; that does not make an integration branch a trusted governance source. The PR event may still create a skipped job/check for an integration target, but the job-level condition prevents execution and runner allocation; skipped is not validation evidence. Internal PRs into a registered integration branch use the Skill and project review process. Do not add this inapplicable metadata check as a Required Check on those branches, or claim an intermediate integration merge delivered the work to the default branch.

For governance metadata inspection, use a reviewed workflow and validator from the trusted default branch. Pin third-party actions by immutable commit SHA, grant minimum explicit `permissions`, avoid secrets and write tokens, and read PR body, changed-file list, labels and review/status data through the API. Do not checkout or execute PR scripts, schema files, dependency installs, or template commands inside a privileged metadata job. Do not interpolate untrusted PR text directly into shell commands. If `pull_request_target` is needed, it is only for this non-executing metadata path; if the host's policy or safe architecture does not allow it, do not enable that version. Business tests of untrusted PR code run in separate low-permission jobs without privileged caches/secrets. [GitHub event/security guidance](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows), [secure `pull_request_target`](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target).

The first governance PR cannot use its own newly proposed default-branch workflow as proof that the validator is trusted. Human review and local validation complete bootstrap under existing protections. After merging the workflow, read it back from default branch, run it against a representative PR, record run URL, head SHA, exact check context/source and result, and verify it behaves on edits and new commits. A Required Check is a **later, separate** proposal. If merge queue is in use, verify a matching `merge_group` event. Avoid path filters, skipped jobs or cancelled runs that leave a required context absent or stale. A required check must not depend on its own success; recheck authorization, reviews and PR HEAD before merge when events cannot reliably invalidate an old green result. [GitHub required check troubleshooting](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks).

## Check and review satisfiability before protection

Before proposing a Required Check, identify the actual check name and source App from a successful trusted run on the relevant SHA. Confirm the context is produced for normal PR updates and, if applicable, merge queue, with the intended branch and event filters. Show existing required contexts and the candidate addition. Ask: “是否**单独批准**把实际跑通的 `<context>`（来源 `<app-id>`）加入 `<branch/ruleset-id>` 的 Required Checks，保留全部现有检查？” Apply only after exact approval and read back both rule and PR merge state. If the check has not run, defer; do not create an impossible required context. GitHub supports source-specific checks on some protection APIs; verify live API support and actual source before binding it. [Branch protection API](https://docs.github.com/en/rest/branches/branch-protection), [status checks](https://docs.github.com/en/pull-requests/reference/status-checks).

Before proposing Required Reviews or `require_code_owner_reviews`, verify a second GitHub account, distinct from the PR author account, is able to submit the needed native review on representative governance PRs. For CODEOWNERS, verify every relevant owner user/team has required repository access, that the team is visible where required, and that line order/pattern precedence yields the intended owner. A second Agent under the author account provides protocol review evidence only. If no eligible second account is verified, do not enable a new native review gate. Existing gates remain in force; report the blocker instead of lowering their count, disabling them, bypassing, or pushing directly. [GitHub review rules](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/reviewing-proposed-changes-in-a-pull-request), [CODEOWNERS](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners).

## Rulesets and branch protection

Read repository Rulesets with `gh api --paginate 'repos/OWNER/REPO/rulesets?includes_parents=true'`, each candidate by numeric ID, and `gh api repos/OWNER/REPO/rules/branches/BRANCH` for effective active rules. The list includes inherited organization Rulesets; record `source_type`, `source`, `id`, `target`, `enforcement`, `conditions`, `rules`, and visible `bypass_actors`. The API may omit bypass actors without sufficient right; unknown is not empty. Record existing branch protection separately. A proposed name matching an existing Ruleset is a conflict, not proof of ownership. If the previous stable ID and managed-field baseline are missing, offer leave-untouched, new noncolliding Ruleset, or a separately reviewed nonweakening takeover. Do not automatically update the same-name object. [Ruleset REST API](https://docs.github.com/en/rest/repos/rules#update-a-repository-ruleset), [about Rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets).

For each Ruleset or branch-protection item:

1. Confirm effective Agent ceiling permits the action. Repository Ruleset edit generally needs GitHub Admin or a verified custom role with edit-rules permission; REST fine-grained permission is Administration write. Repository Actions settings and branch protection similarly need Administration write. Maintain alone is insufficient for these settings. Verify actual endpoint right, host/version/plan availability and whether an organization rule is immutable to this repository actor.
2. Show current/inherited protection and full proposed effect: targeted refs, PR requirement, reviewer count, CODEOWNER requirement, conversation resolution, Required Checks with sources, linear history, force push, deletion and bypass actors. Keep every existing stronger requirement. Ruleset union or inherited policy can make effective behavior stricter than a single candidate. A source with two required reviewers remains two; a one-reviewer template cannot offer reduction as an approval option.
3. Ask one question for this exact resource: “是否批准创建/修改仓库 Ruleset `<id/source>` 的所示字段？” or “是否批准分支 `<ref>` 的所示完整保护差异？” A Required Check or new native review gate within either resource still needs its own prerequisite check and explicit approval. An organization Ruleset must be handled by an authorized organization actor through a separately proposed scope; this repository Skill does not claim it.
4. Re-read by ID and compare approved digests immediately before write. For a registered repository Ruleset, GET the complete current object, preserve all unowned fields and complete `conditions`, `rules`, and `bypass_actors` arrays, approve each changed field, then use the documented `PUT /repos/{owner}/{repo}/rulesets/{ruleset_id}` with a complete preservation-safe payload. Never use a partial bundled template as the full body. Branch protection `PUT` has required fields and can disable settings via `null`; build the entire preservation-safe payload from current state. If complete preservation cannot be verified, stop and ask for a manual owner action.
5. Read the resource and effective rules back, then inspect a representative PR's actual merge requirements. Record returned ID and fields. If network outcome is unknown, query by ID or exact repository/type/name before retry. A 2xx command alone is not proof that the repository now enforces the intended gate.

Actions, Rulesets, and review capabilities can vary by host, product plan, organization policy and time. At runtime consult the linked official docs and live repository read endpoints. Record an unavailable/unknown capability rather than inventing a quota or claiming enforcement. If GitHub enforcement is unavailable, the collaboration protocol and human Leader review still apply; report that GitHub cannot enforce that part automatically.
