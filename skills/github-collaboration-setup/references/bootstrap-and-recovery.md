# Bootstrap and recovery

Read [preflight](preflight-and-identity.md) and [authorization](authorization.md) first. These procedures only permit an explicitly approved governance setup or repair. The daily collaboration Skill is not required to finish this scoped work; ordinary feature development still follows the daily workflow.

## Select the entry path

| Observed state | Next safe action |
| --- | --- |
| Existing repository, account permission below Maintain or unknown | Stop at read-only findings. Ask an eligible human/account to proceed. |
| Existing repository, no installed authorization, account verified Maintain/Admin | Ask the human to explicitly grant this responsibility-based `actor_id` a scoped Bootstrap Leader session for this repository and source SHA. Until granted, Agent remains Member. |
| No Git and/or no GitHub repository | Inventory files and credentials without disclosing secret contents. Ask the human for owner/name/visibility and separate approval of each creation step below. Proposed repository identity is not verified permission or a persistent grant. |
| Existing authorization file, every Leader lost/revoked | Use scoped Recovery, not Bootstrap. Retain file and history; ask a human controlling a verified Maintain/Admin account to grant a narrowly bounded Recovery Leader session. |
| Existing active Leader | Use that validated delegation for the proposed setup action; no Bootstrap shortcut. |

### New repository creation sequence

1. Confirm target local directory, current Git status, proposed GitHub host, owner, repository name, and visibility. Before creation, ask whether the human intends to grant the named `actor_id` a bounded Bootstrap Leader session for that target; this is only a conditional intent, **not an effective grant**, because repository ID and default-branch source SHA do not exist yet. If the user lacks an account, give the official GitHub signup link from preflight and pause remote work. If local authentication is missing, use browser login guidance; never request a token in chat.
2. Show exact local Git initialization effect and request approval **for Git init** if Git is absent. Do not change existing history.
3. Show host/owner/name/visibility and request separate approval **to create the remote repository**. Create only that approved resource, then read back its immutable repository ID, URL, visibility, default-branch state, authenticated account stable ID, and actual permission. If permission is below Maintain or cannot be confirmed, stop; report the created resource and completed steps without deleting it.
4. If no default-branch commit exists, show a minimal initial-commit manifest with every included path and a secret/generated/large-file check. An empty commit is acceptable. Never use `git add .`/`git add -A`, capture unapproved user changes, or include `.github/workflows/**`, the configured/proposed authorization file (including the default `.github/agent-collaboration/authorization.yml`), or other governance content. Request separate **Commit** and **Push** approvals. Only this first branch-establishing commit may go directly to the default branch; it does not install authorization.
5. Read back the created default branch, source commit SHA, account permission, protections, and repository identity. Ask the human to reconfirm the earlier Bootstrap intent as an effective, scoped session grant for the chosen `actor_id`, bound to these verified values and a named governance proposal. Earlier creation approvals or conditional intent cannot supply that grant. If the first commit/push is blocked, report the existing rule or missing authority; never force push or weaken protection.

For an existing repository, begin at step 5 after validating its current default branch, history, and protections. A repo with existing history never takes the direct-first-commit exception.

### Governance PR and persistence

1. Under the scoped session, create the configuration Issue and publish its scoped claim; neither Issue creation nor the initial claim requires a prior implementation claim. Record the claim URL, then prepare an isolated `agent/<actor_id>/issue-<primary_issue>-<description>` branch from the verified default-branch SHA. Draft the authorization record at the active config's `managed_paths.authorization`, or at the explicitly approved candidate path for a first installation. The proposed fields bind host, repository ID, owner/name, default branch and source SHA, `controlled_by`, stable `controlled_by_id`, responsibility-based `actor_id`, and the human-approved ceiling. Before content approval, compare these fields with the schema requirements except the unavailable approval evidence; this incomplete draft may not merge. After the evidence-only commit, validate the complete record with the bundled schema and `FormatChecker()`. A proposed `active` status in the branch is future state, not current authority.
2. Show each local file diff and seek approval for it. Ask separately for Commit, Push, and PR creation. Before a Push that can trigger Actions, apply its own disclosure and approval gate. Build the PR from the selected project template, retaining its human-readable structure and one JSON metadata block with `workflow: "setup"`, the current HEAD, base branch and claim URL; [local configuration](local-configuration.md) defines the handoff checks. A configuration Issue and PR are part of this scoped session; they do not bypass existing required reviews, checks, CODEOWNERS, Rulesets, or branch protection.
3. Before content approval or the evidence-only step, resolve authorization's existing registry ownership, if any, through [managed resources](managed-resources.md). Once the governance PR has a stable URL and content HEAD `P`, ask the human to approve **this authorization content and `P`**. Store `approved_head_sha=P` in a follow-up evidence-only commit `E`; compare `E` with `P` and reject any change beyond the approval evidence. Obtain and verify external final-`E` approval through [authorization](authorization.md), including its equivalent documented human approval path and actual native review requirements. Respect dismissal of earlier reviews and all existing gates. A later content change restarts both approvals. Re-read default-branch rules and account permission before merge. If an actually required reviewer or check is unavailable, leave the PR pending and report the blocker; disclose known unsupported enforcement without treating unknown rules as absent.
4. After authorized merge, re-read config and the authorization at `managed_paths.authorization` from the verified default branch at the same new commit SHA. Validate their schemas/URI/date formats, repository identity, account/actor match, approved content HEAD `P`, external final-`E` approval, active status, and frozen ceiling. Only after this read-back does the Agent become a **persistent Leader by default**; the user need not repeat the grant in later sessions. Keep final approval, merge SHA, and read-back SHA as external evidence. If the read-back fails, remain at Member/session status and report the discrepancy.

Until step 4 succeeds, Bootstrap authority belongs only to the current session and the approved scope. On interruption, changed account/actor/branch/source SHA, or stale proposal HEAD, stop and get a fresh human confirmation after a new preflight. The setup Skill cannot use a candidate PR to authorize itself.

## Lost last Leader recovery

1. Resolve the authorization path from config at the verified default-branch SHA and inspect that exact path at the same SHA. Distinguish revoked, superseded, unreadable, and missing records. Read the old protocol, protection, and approval rules from that branch. Do **not** delete or rename the configured authorization file to simulate first installation, clear history, bypass checks, or reduce required reviews.
2. Verify the human's controlling account is currently Maintain/Admin. Show the exact recovery proposal, target account/actor, ceiling, repo/source SHA, allowed operations, and expiry at end of this session; obtain an explicit scoped Recovery Leader grant. A Maintain/Admin account alone is still a Member Agent.
3. Propose an independent governance PR under the **old** rules. Preserve prior delegation records and mark status changes explicitly. The human approves the proposed PR HEAD, and all existing review/check/protection gates must pass. If the only eligible reviewer is unavailable, stop with a pending PR and report the human action needed; recovery is not an exemption.
4. Merge only after rechecking old authority, account permission, proposal HEAD, and gates. Read back config and its configured authorization record from the default branch at the same merged SHA, with schema and `FormatChecker()` validation. Only then can the new delegation be used persistently. An interrupted Recovery session requires a fresh scoped human grant.

For an Admin ceiling requested through a Maintain Leader, the same recovery-style, human-authorized **Admin-account session** may be used only for the named escalation PR. The existing Maintain Leader cannot grant or approve Admin to itself. The record takes effect only after explicit human approvals, merge under the actual applicable protocol/protection gates, and read-back as [authorization](authorization.md) specifies.
