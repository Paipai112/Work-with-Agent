# Review, merge, and post-merge

Read [preflight](preflight.md), [identity and permissions](identity-and-permissions.md), [claims and handoffs](claims-and-handoffs.md), and [Git and pull requests](git-and-pull-requests.md) first. This procedure applies to both business and governance PRs; governance proposals additionally require `github-collaboration-setup` and their own approvals. Never use account Admin/Maintain alone as proof of Leader authority. Refresh repository ID, default-branch HEAD, account permission, default-branch delegation, and Issue/PR/claim state before review or merge. A permission drop below Maintain immediately removes effective Leader authority; a later upgrade does not raise a stored ceiling.

## Two distinct review gates

Reviewers need no implementation claim. Reuse substantive engineering review evidence for the exact current HEAD/scope when it identifies reviewer, findings, validation and limitations. An authorized reviewer must verify that evidence, resolve uncovered protocol/acceptance questions, and publish the formal record below; another tool's review is not automatic Leader approval. Changed HEAD invalidates the approval; prior findings may guide re-review but do not certify the new version.

1. **Protocol review.** Inspect the current PR diff, exact changed-file scope, Issue acceptance criteria, test evidence, risks, active claims, and current HEAD SHA. Another responsibility identity with a **currently effective Leader delegation**, or the human project owner, must publish a review record for that exact SHA. The implementation `actor_id` cannot be its sole protocol reviewer. Use [review-record.yml](../templates/review-record.yml) as a shape, replace all example data, post in the PR discussion, capture its comment ID/URL, and read it back. The record must identify repository/PR, implementing and reviewing identities, reviewer account, reviewed HEAD, scope, evidence, conclusion, time, and limitations. `comment`, `approve`, and `request-changes` are protocol conclusions; none alone changes GitHub's native review state. Distinct actors sharing one account create collaboration evidence, **not** independent-account security proof.

   On read-back, independently verify the GitHub comment's immutable repository ID, exact PR number, comment ID and URL, actual `user.id` and `user.login` against the record's `reviewer_account_id` and `reviewer_account_login`, and the reviewer actor's **current** default-branch Leader delegation plus that account's **current** repository permission. Resolve the URL and ID to the same comment on this PR; reject a pasted URL, body-provided account, stale authorization, changed account identity, or apparent Leader title unsupported by GitHub metadata and the pinned default branch. For a human owner review, verify the real account and project ownership/authorization rather than accepting a body self-claim. A comment with genuine authorship but revoked delegation is not a current valid protocol approval.

   Merge requires an authenticated `approve` record from that other Leader/human owner for the **current** HEAD. `comment` is feedback, not approval. Any outstanding valid `request-changes` blocks merge until a later authorized record explicitly resolves or withdraws the named concern and records `approve` for the current HEAD after re-review. An implementation actor's own `approve`, an older-HEAD `approve`, and a bare "fixed" claim cannot satisfy this gate.
2. **GitHub native reviews.** Query current reviews, reviewer account IDs, submitted states, branch/ruleset requirements, and CODEOWNERS where applicable. The PR author's account cannot supply its own native Approve even through another actor. A protocol comment is not a native Approve. If required reviews cannot be supplied by an eligible other account, stay blocked and report the missing reviewer; do not weaken protection or falsely mark a comment as approval. Where no native review is actually required, the verified protocol/human approval above remains necessary; it is not represented as native Approve. A Member may leave ordinary comments, but cannot complete Leader-only protocol approval or merge.

When the PR HEAD changes, treat earlier protocol review as stale. Re-review the complete current diff and record a new conclusion bound to the new SHA. Re-evaluate GitHub native review requirements for the new HEAD under actual repository settings; a displayed old `reviewDecision: APPROVED` is not sufficient evidence that the current HEAD passed this protocol. Old green checks are likewise not current-head checks.

## Merge gate

Immediately before merge, read back all of the following for the *same current PR HEAD*: effective Leader authority and current account permission; uncontested active claim and Issue lineage; whole changed-file list and governance reachability; a verified, current-HEAD protocol `approve` by another actor/human owner with no unresolved `request-changes`; native reviews and CODEOWNERS actually required by applicable rules; required checks with their SHA, conclusion, and required source; resolved conversations; PR base/default branch, mergeability, and repository branch protections/rulesets. Failed, pending, missing, stale, ambiguous, or untrusted evidence blocks merge. Disclose verified unsupported enforcement or an unprotected target; unreadable/unknown applicable rules stop the affected write. Do not bypass branch protection, disable checks, dismiss reviews, or blend governance files into a business PR. If Actions may run on merge, make the applicable trigger/cost notice before the write.

Record the reviewed 40-character HEAD SHA and use GitHub's merge operation with an **expected HEAD SHA / SHA lock**; a changed HEAD rejects the attempt and restarts review rather than merging by PR number alone. Choose merge method only as allowed by the confirmed project protocol and protections. Capture PR URL, expected HEAD, resulting merge commit SHA, and response. A timeout or ambiguous response is not proof of failure; use [failure recovery](failure-recovery.md).

## Post-merge read-back

Read the PR merged state and merge SHA, then verify the result is reachable from its actual approved target branch (accounting for merge method). An integration-branch merge records intermediate progress; final delivery requires reachability from the actual remote default branch and completed acceptance. For every linked Issue, inspect acceptance, `closes_issues` and existing events before adding only missing completion/release/handoff evidence or closing it. Include PR URL, target branch, merge SHA, actor, remaining work and successor. Read back Issue state and event IDs/URLs; avoid duplicate closure after uncertain responses. If updates fail, retain merge proof and recover idempotently.
