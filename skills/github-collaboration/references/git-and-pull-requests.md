# Issue-linked Git and Draft PR work

Read [preflight](preflight.md), [identity and permissions](identity-and-permissions.md), and [claims and handoffs](claims-and-handoffs.md) first. For implementation and Git writes, the Issue must be open and this actor/session must hold a read-back-verified uncontested code claim covering the exact paths. Apply the confirmed default-branch protocol and package verification timing from preflight. Issue creation and review use their own operation prerequisites.

## Branch and file boundary

1. Create or use `agent/<actor_id>/issue-<primary_issue>-<short-description>` from a verified **commit SHA** on the default branch or an approved integration branch listed in the pinned config's `branch_policy.integration_branches` (absent means empty). Integration branch names follow the same responsibility/primary Issue pattern. Record the chosen `base_branch` and fetched base SHA in the task; do not substitute an unverified local ref. Example: `git switch -c agent/backend-api/issue-55-payment-timeout-retry <confirmed-40-char-SHA>`. Authorization always comes from the confirmed default branch, including work based on an integration branch. Never commit daily work on the default branch. Reuse an existing branch only after checking HEAD and claim lineage; unknown old process status requires a distinct branch under the reassignment procedure.
2. Inspect `git status --short`, the unstaged and staged diffs, untracked files, and each intended file's relation to the owned claim. Preserve pre-existing user changes; if the work cannot be separated safely, stop and ask. Run relevant tests and scan intended staged content and filenames for secrets, credentials, `.env`, private keys, generated sensitive outputs, and out-of-scope changes. Do not print secret values in reports or PRs.
3. Stage **only** inspected exact paths: `git add -- src/api/retry.py tests/api/test_retry.py` is an example, not a prescribed path list. `git add .` and bare `git add -A` are prohibited. A path-limited `git add -A -- <exact paths>` is only potentially acceptable when the **confirmed default-branch project protocol explicitly allows it** and every named path and deletion has been inspected; the current project template protocol forbids even that form, so use `git add -- <exact paths>` there. Never use globs whose expansion can include unrelated files. Review `git diff --cached --name-status` and `git diff --cached --check` plus the full staged diff; verify it matches the claim and contains no secrets. If not, undo only the unintended staging after examining the index, without discarding user content.
4. Commit with an Issue reference and descriptive `actor_id` in the message or trailers, recording real test evidence. Do not invent a pass result. Avoid rewriting published history or silently changing another Agent's commit.

## Governance separation

Before stage, commit, push, or moving a PR to Ready for Review, compare the entire changed-file list and actual diff with the confirmed project's managed paths. Protocol, config, authorization, managed-resource inventory, collaboration schema/check implementation, and labels/templates/workflows/ruleset proposals are governance. Apply the checker's conservative whole-file classification to every entry registered in trusted `managed_paths.entry_files`; when that field is absent, use `AGENTS.md`, `CLAUDE.md`, and `CONTRIBUTING.md`. Edits outside the managed block, including ordinary project prose, still require governance review. Nested `AGENTS.md`/`CLAUDE.md`, `AGENTS.override.md`, and instruction-loading resources also follow governance routing. Inspect both old and new paths for a rename. A missing patch does not exempt a registered or instruction entry; obtain the actual diff before approving its changes. Inspect changes outside those paths for effects on managed-block or installation-link reachability. The checker classifies paths conservatively; it does not prove arbitrary prose has no instruction effect.

Keep the business PR at Draft, separate governance from Issue-scoped work without overwriting existing edits, and route the governance proposal through `github-collaboration-setup` as an independent PR by a currently verified Leader. An Admin account or a new Leader grant inside the business branch does not make that Agent Leader on the confirmed default branch. If separation would lose changes or there is a conflict, obtain the user's choice before changing anything.

Whole-file governance review is a review boundary, not managed ownership or permission to replace the file. Setup may modify only the precisely approved managed block or resource. Any proposed change to user-owned prose, an installation link outside the block, or a move to another document needs its own reviewed diff and explicit approval. Existing dirty edits also need the user's separate treatment and Commit-ownership choices; file registration, a code claim, or approval of the block alone does not authorize staging the entire file.

## Immediately before push

Re-read the active claim, related Issues/PRs and competing scopes; fetch the exact target remote branch and compare its HEAD with the SHA used to prepare the local update. Recheck the confirmed default-branch HEAD and relevant authorization if changed or stale. A changed claim, conflicting scope, unexpected remote HEAD, uncertain account permission, or governance contamination stops the push. Never force-push or bypass branch protection. A network timeout or ambiguous push response is **unknown**, not failure: read the remote ref, PR/Issue events, and GitHub status before deciding whether a retry is safe. After a successful push, read back the remote HEAD and relevant claim state.

Before a push, PR creation, merge, or workflow dispatch that may trigger Actions, inspect configured workflows and actual triggers. Tell the user which workflow may run, the runner and known quota/cost implications, and any uncertainty. Enabling an Action or making it a Required Check belongs to setup with its own advance approval; do not silently activate, stage, or push a new workflow. An existing workflow still merits notice before the first operation that may trigger it under this protocol. Do not claim exact charges without a verified plan/usage source.

## Draft PR

Read `managed_paths.pull_request_template` from the confirmed default-branch config/SHA when configured; otherwise use the repository's applicable PR template. Do not assume GitHub auto-applies a multi-template file. Inspect the pushed HEAD, base and existing PRs, then create a **Draft** PR with an explicit body/base/head and read it back.

Preserve the project's or engineering tool's body structure. Include scope, Issue acceptance criteria, real commands/results and untested areas, risks/rollback, Actions notice, remaining work and handoff. [The bundled body](../templates/pull-request-body.md) is an example, not a mandatory heading layout. Add exactly one `<!-- agent-collaboration:metadata` HTML comment containing a JSON object, closed by `-->`. Its exact fields are `schema_version: 1`, `primary_issue`, `closes_issues`, `actor_id`, `controlled_by`, `controlled_by_id`, `runtime`, `session_id`, `skill_version`, `head_sha`, `base_branch`, `claim_urls`, and `workflow: "daily"` (`"setup"` is reserved for setup-managed governance).

`primary_issue` is a positive integer matching the branch name. `closes_issues` is a deduplicated positive-integer list, possibly empty for partial delivery; it can include multiple Issues and need not include the primary Issue. Explicit closing statements must match it exactly. `claim_urls` is a nonempty, deduplicated list of verified claim comment URLs from this repository, covering the changed scope and related task/actor lineage. Include at least one claim on the primary Issue; related claim Issues need not be closed by this PR. The checker confirms linked Issues exist and are not PRs, but the Skill/reviewer must verify the comments, authors, lineage and scope. `head_sha` is the current pushed full SHA; `base_branch` is the actual approved PR target. Keep machine identity/version/HEAD data in this one block, with no duplicate JSON keys or contradictory metadata. The checker validates declared metadata, not prose meaning, actual Skill loading, running processes or review quality.

Internal PRs may target an approved integration branch. Their merges are intermediate progress, not delivery to the default branch: keep final-delivery Issues open and carry their acceptance/claim evidence into the final PR. The optional v0.1 trusted metadata Action applies only to final PRs targeting the default branch; do not require that inapplicable check on integration PRs. Use the Skill and project review gates there. A passing test or metadata check alone never makes a PR ready or approved.
